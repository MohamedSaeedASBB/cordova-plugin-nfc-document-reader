1. What this component is, and what it is not

A Cordova plugin embedded in the bank's mobile application. It reads ICAO 9303 electronic identity documents (passports and national ID cards) over NFC, scans the printed machine-readable zone with the camera, photographs the document, runs a challenge–response liveness check, and compares the holder's face against the portrait stored on the document's chip.

It is a data-collection and evidence-gathering component. It is not a decision engine. It returns measurements — a chip payload, a similarity score, a set of checks that passed or failed — to the host application, which forwards them to the bank's backend. The accept/reject decision, and every threshold behind it, lives in the backend and is deliberately not shipped in the app.

5. Network egress — the assessment question

NO EGRESS   Plugin code opens no network connections

Every network primitive on both platforms was searched for (HttpURLConnection, URLSession, dataTask, openConnection, Socket, http://, https://). There are no matches in the plugin's source. No document data, chip data, biometric data or image ever leaves the handset by an action of this component.

5.1 Change history — a removed exfiltration path

Until commit a94c3b1 (28 September 2026) this was not true, and assessors reviewing an earlier build must treat it as a finding.

Earlier revisions POSTed every NFC read failure to a third-party Supabase project belonging to the plugin's original developer, on both platforms. The payload carried a partially masked document number (1139***06), a partially masked date of birth (97***2) and expiry, the host application's bundle identifier, the handset model and OS build, chip protocol details, and up to 2,000 characters of reader internals. The endpoint and its API key were XOR-obfuscated in source, with an accompanying comment stating the purpose was to prevent extraction from a decompiled build.

The masking did not anonymise the data. Four leading and two trailing digits of a nine-digit document number leave one thousand candidates; a birth year and a bank's bundle identifier reduce that to one individual. The network path has been deleted — not disabled behind a configuration flag — and the diagnostic loggers now write to the device log only, with the MRZ arguments deliberately never written.

5.2 Residual egress that is not ours

PRESENT   Google ML Kit emits usage and diagnostic analytics

ML Kit performs inference on-device — no face or document is uploaded for processing. However the SDK reports usage and diagnostic data to Google. Evidence taken from the pods resolved for this build, not from documentation:

  • MLKitCommon.framework contains the endpoints https://play.googleapis.com/log and /log/batch, and a class MLKAnalyticsLogger.
  • It depends on GoogleDataTransport, whose Apple privacy manifest declares collection of OtherDiagnosticData for Analytics.
  • Google's own privacy manifest for MLKitFaceDetection declares collection of: DeviceID, OtherUserContent, OtherDiagnosticData, PerformanceData, ProductInteraction, OtherDataTypes. NSPrivacyTracking is false and no tracking domains are declared.

OtherUserContent in a face-detection SDK is the item requiring clarification from Google before any statement that no data leaves the device is signed. No comprehensive opt-out is documented for standalone ML Kit; FIREBASE_ANALYTICS_COLLECTION_ENABLED governs a different component.

5.3 Options available to eliminate it

OptionWhat it involvesAssessment
Remove ML Kit from iOS Apple Vision already performs all OCR on iOS and also detects faces, landmarks and head pose on-device with no analytics component. Vision does not expose smile and eye-open probabilities, so those must be derived from eye and mouth landmarks, and the liveness thresholds recalibrated. Well-understood work. Removes the last third-party network component from the iOS build.
Remove ML Kit from Android ML Kit supplies both the OCR and the face detection there. Replacement means bundling a text recogniser and a face detector as TFLite models. Substantially larger, with a model-governance question attached to each model.
Network policy ML Kit's traffic goes to play.googleapis.com, which a managed-device policy can observe and block. A mitigation, not a fix. Whether it suffices is the bank's decision.

Consequence for the bank

The plugin hands biometric data to the host application in a single JSON payload. Everything that matters for retention, encryption at rest, access control and consent is therefore a property of the application and the backend, not of this component. A payload can exceed 1 MB; it must be treated as biometric personal data from the moment the callback fires.

8. Trust model for document authenticity

Passive authentication decomposes into three independent checks, each reported separately rather than collapsed into one boolean:

CheckReported asMeaning
SOD signature validsodSignatureVerifiedThe Document Signer's signature over EF.SOD verifies.
Data-group integritydataIntegrityVerifiedEvery data group hashes to the value EF.SOD records.
Issuer trustedissuerTrustedThe Document Signer chains to a CSCA in the bundled trust store.

The first two checks pass for a forger who signs their own data with their own certificate. Only the third makes the result mean "signed by the state that claims to have issued this document". Without a CSCA bundle installed the status is notVerified / NO_TRUST_ANCHORS — not a failure, but not evidence of authenticity either. A CSCA bundle is not currently installed.

9. Security controls: what each proves, and what it does not

ControlEstablishesDoes not establish
Chip read (BAC/PACE)The document carries a genuine, readable MRTD chip whose access key matches the printed MRZ.Anything about the person presenting it.
Passive authenticationThe data groups are byte-for-byte what the issuer signed, and the signer chains to a trusted CSCA.Not clone detection. A bit-perfect copy of a genuine chip passes. Chip Authentication detects cloning; it is reported but not relied upon.
MRZ ↔ chip comparisonThe print and the chip agree across seven fields, with a per-field edit distance.A mismatch may equally be OCR misreading worn print — it is a finding for a human, not proof of fraud.
Document evidence checkThe photograph shows the document that was just read — MRZ shape plus identifiers taken from the chip.Not liveness of the document. Cannot distinguish a card from a photograph of a card or one displayed on a screen.
Liveness challengesA printed photograph or a still image did not pass. Eight challenges, randomly ordered, four requiring two simultaneous actions.Not defeated: a replayed video, an injected or virtual camera feed, or a 3D mask. There is no presentation-attack detection.
Session videoAn auditable record of what the customer actually did.No improvement to attack detection — a replay attack is simply recorded.
Face matchA cosine similarity between the liveness portrait and the DG2 chip portrait, computed on-device.Not a decision. No threshold is applied in the app; the backend decides.
